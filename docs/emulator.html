1一句话说明

这个模拟器不重写电台的功能，而是在电脑上虚拟出一台 IC-705 的主板： CPU、内存、闪存、GPIO、SPI、I²C、串口、LCD 控制器、定时器、中断控制器，以及一颗副 CPU。 然后把 Icom 官方固件原封不动地放进去运行。屏幕上看到的每个像素、菜单、开机动画，都是原版固件自己画出来的。

关键原则：固件一条指令都不改，也不在固件里打钩子（hook）。 固件读写的每个硬件寄存器，都由一个按真实芯片行为编写的“外设模型”来响应。 只要模型的行为和真芯片一致，固件就分辨不出自己跑在模拟器里。

3从固件包到屏幕

3.1 准备固件（decoder/ + ic705_emu.py）

  1. 读取 Icom 的 705E140.dat。它是加密、压缩后的打包格式。
  2. decoder/ic705_decode.py 解密（autokey）、LZSS 解压，拆出各个部分：主程序区、副 CPU 程序 aux2、DSP/FPGA 组 dsp.image.bin、WLAN 固件。
  3. 启动器按真机闪存布局拼出 16 MiB 的 flash.bin：主程序放在 0 地址，字体和图片资源放在 0xC00000。这就是主 CPU 上电后从 0x18000000 读到的 QSPI 闪存内容。
  4. 结果缓存在 ~/.local/state/ic705/<固件哈希>/。同一目录里还有 eeprom.bin，保存电台设置。

3.2 上电与开机（全部由原版固件完成）

  1. 复位：主 CPU 从闪存里的引导程序开始执行，把加载器复制到 0x20004000，再把主程序解压到 RAM 0x20005000。
  2. 深度待机：没有检测到开机原因时，固件让芯片进入深度待机（WFI 停在 0x2007848C），副 CPU 也进入 STOP 睡眠。
  3. 按 POWER：启动器通过 QMP 把 P3_9 拉低 3 秒。模型按真芯片的行为做“深度待机解除”：复位 A9，并在 DSFR 寄存器里记下唤醒原因是 POWER 键。如果 EEPROM 里记着上次是开机状态，固件会自己开机，启动器就不再按键。
  4. 完整初始化：Keil RTX 实时系统启动各个任务，依次完成：
    • 按 Altera 被动串行时序配置 FPGA（nCONFIG / nSTATUS / CONF_DONE）；
    • 通过 GPIO 模拟的软件 I²C 从 EEPROM 读出约 104 KB 设置；
    • 通过 RSPI3 发命令、从 RSPI4 闪存把程序流式送进主 DSP，等 P7_7 应答；
    • 通过 SCIF3 与副 CPU 握手，副 CPU 报告版本 1.20-E00；
    • 初始化充电芯片、RTC、触摸屏、ADC 按键电阻梯等。
  5. 显示：固件用 OpenVG 绘制界面，再由 VDC5 合成到 480×272 的帧缓冲。QEMU 把帧缓冲显示在 GTK 窗口里。先出现 ICOM 开机画面，然后是主界面。

4怎样做到“真正的硬件仿真”

4.1 CPU：动态二进制翻译

QEMU 的 TCG（Tiny Code Generator）把一小段 ARM 指令（一个“翻译块”，TB）翻译成 x86 机器码，缓存起来反复执行。 主 CPU 和副 CPU 是同一个 QEMU 进程里的两个 CPU，型号分别是 cortex-a9 和 cortex-m0，各自执行自己的原版固件。 CPU 本身（指令、异常、MMU、缓存维护指令等）由 QEMU 上游实现，这部分已经很成熟。

4.2 外设：寄存器级模型

真正的工作量在外设。CPU 访问外设地址（例如 0xFCFE3208）时，QEMU 不访问内存，而是调用对应外设模型的读写函数。 模型要做的就是像真芯片一样回应：

  • 寄存器语义一致：同样的地址、同样的位定义、同样的“写 1 清零”“读后清除”等副作用。例如 GPIO 的 PSR 寄存器，高 16 位是写使能、低 16 位是数据。
  • 时序一致：定时器按虚拟时钟计数，中断在正确的时刻触发，SPI 一个字节对应一次收发。
  • 引脚级连接：芯片之间按原理图连线。主 CPU 的 SCIF3 同步串口接到副 CPU 的 SPI1 从机，另有 4 根 GPIO 握手线；按键电阻梯接到 ADC；触摸屏是 GPIO 上软件模拟的 SPI。
  • 外部器件模型：I²C EEPROM（24M02 类，256 KiB，写入持久化到文件）、充电芯片（BQ2571x 类）、RTC（RX-8803）、SPI-NOR 闪存（IS25LP128）、触摸屏 ADC（TSC2046 类）。

4.3 模型从哪来：用固件本身做“规格书”

Icom 不公开电路细节，RZ/A1H 和 STM32 的芯片手册也只说明芯片本身，不说明板上怎么连。 所以每个模型都是先从固件代码里读出来的：固件往哪个寄存器写什么值、等哪个状态位、在哪个中断里处理什么。 例如 FPGA 配置握手： 

0x2011D1F4  str  r6, [r7, #0x108]     ; PSR2 = 0x40004 → P2_2 (nCONFIG) 拉高
0x2011D220  ldrh r0, [r5, #8]         ; 读 PPR2（0xFCFE3208）
0x2011D224  tst  r0, #8               ; 等 P2_3 (nSTATUS) 为高
...
0x2011D28C  tst  r0, #0x80            ; 等 P2_7 (CONF_DONE) 为高

从这几条指令就能确定引脚分配和握手顺序，再对照 Altera 被动串行配置的公开时序，写出 GPIO 里的 FPGA 配置模型。 所有结论都标注证据来源：

标签含义
[FW]直接从固件字节或反汇编读出（静态、确定）
[VM]在模拟器里观察到（不一定是真机行为）
[EXT]外部资料：维修手册、芯片手册、其他项目
[INF]推断，未验证

4.4 验证：拿真实行为做对照

  • 正向对照：例如单独调用固件里的 CRC32 函数，结果和 zlib 一致，说明 CPU 和内存映射正确。
  • 端到端行为：副 CPU 报出的版本号、设置能写进 EEPROM 并在重启后保留、触摸位置和真机校准一致、主旋钮 100 格 = 1 kHz。
  • 不改固件：任何“为了让它跑起来”的捷径都放在外设模型里，并且有开关，可以随时关掉对比。

4.5 行为模型与完整模拟的区别

并不是每颗芯片都值得完整模拟。FPGA 负责射频信号处理，它的比特流是专有格式，没法“执行”。 对固件来说，只要配置握手的引脚按时序给出回应，后续流程就和真机一样。这类只模拟固件“看得到的那部分行为”的叫行为模型。 主 DSP 的启动应答也属于这一类。真要让 DSP 处理音频，就得运行它自己的固件（见第 7 节）。

6时间模型与性能

6.1 为什么用 icount

固件里有大量“等某个状态位，超时就放弃”的循环，还有依赖定时器的协议。 QEMU 的 -icount shift=1 模式让虚拟时间严格由执行的指令数决定（每条指令 2 ns）， 结果完全可复现，也不会因为宿主机忙闲而改变固件看到的时序。代价是：所有 CPU 只能在一个宿主线程里轮流执行。

6.2 开机慢在哪里

用 QMP 采样 CPU 的 PC、读 OSTM 计数器换算虚拟时间、用 perf 剖析宿主，得到原版的开机时间线：

阶段虚拟时间原因
等 FPGA 配置（P2_3/P2_7）≈ 3.2 秒FPGA 不存在，等到超时
软件 I²C 读 EEPROM≈ 3.0 秒真机也要这么久，属正常
等主 DSP 启动（P7_7）≈ 2.0 秒DSP 未运行，等到超时
其余初始化≈ 0.8 秒—

更严重的是：虚拟时间只有真实时间的 5% 左右。两颗 CPU 都在紧密轮询 GPIO， 而原版 QEMU 在 icount 模式下每读一次外设寄存器都要“倒回去重新翻译”一次， perf 显示真正执行翻译后代码的时间只占百分之几。

6.3 做了哪些优化

优化位置原理
I/O 指令单独成块qemu/patches/icount-io.patch（QEMU 核心）icount 要求访问外设的指令必须是翻译块的最后一条。原版每次都靠异常回退、查树、恢复状态再重新生成。现在第一次发生后记住这条指令的地址，重新翻译时让它单独结尾，以后直接执行。
外设总线等待周期同上，--io-wait，默认 128真机读外设要走慢速外设总线（约 100–250 ns），icount 却只算 2 ns。每次外设访问额外计入 128 条指令（约 256 ns），轮询循环用更少的次数就能走完同样长的虚拟时间。不越过下一个定时器的截止点，结果仍然确定。
按真实主频分配 CPU 时间qemu/patches/icount-rr.patch，--cpu-weights，默认关闭（1,1）QEMU 把每轮时间平均分给两颗 CPU，32 MHz 的副 CPU 因此跑得和 400 MHz 的主 CPU 一样快，白白占一半时间轮询。按 15:1 分配，亮屏可再提前约 10 秒。但主副 CPU 之间的同步串口（SCIF3 ⇄ SPI1）还没有模拟波特率，副 CPU 一放慢就跟不上握手，会报“副 CPU 工作不正常/版本不一致”，所以暂不默认开启。
FPGA 配置握手qemu/machine/gpio.cnSTATUS 跟随 nCONFIG，nCONFIG 拉低后再释放即置位 CONF_DONE。去掉约 3 秒虚拟时间的超时。
主 DSP 启动应答qemu/ic705/dsp.cRSPI3 上看到启动命令 n=1 时拉低 P7_7，n=2 时拉高。去掉约 2 秒的超时。

版本LCD 亮起到主界面

6.4 开机之后为什么还是慢：定时器把时间片切碎了

开机完成后主 CPU 基本空闲，但副 CPU 跑的是一个不停轮询的主循环（单片机固件的常见写法）。用 perf 剖析稳态， 宿主时间里外设模型本身只占约 5%，翻译后的客户机代码只占 2%，其余全是 QEMU 核心在“退出—查表—拿锁—重新进入”。 用 exec_tb_exit trace 和临时统计代码查到原因：icount 模式下每个定时器到期都会结束当前时间片， 而有三个模型在固件并不关心的时候也一直触发定时器：

模型原来现在
SCIF3 只接收模式的时钟（rz_a1h.c）50 kHz 定时器，从开机一直跑到关机只在 SCIF3 处于同步只接收模式时运行，靠 SMR/SCR 写入钩子启停
STM32 定时器（qemu/ic705/subcpu/timer.c）每个计数周期触发一次只有开了中断、TRGO 或单次模式时才预约；SR 标志在固件读写时补算
MTU2（mtu2g.c）每个比较匹配点都触发（PWM 一个周期最多 4 次）只为开了中断的事件预约；计数清零按周期取模推算，TSR 标志在读写时补算

另外 QEMU 的轮转调度器把“到下一个定时器的时间”平均分给所有 CPU，主 CPU 空闲时它那一半没人用， 副 CPU 只能跑一半、再一半……逼近一个定时器要十几轮。icount-rr.patch 改成只在可运行的 CPU 之间分配。 结果：主界面空闲时虚拟时间从真实时间的约 8% 提高到约 25%，开机亮屏从约 36 秒缩短到约 14 秒。

6.5 外设访问的全局锁与多线程

QEMU 每次外设访问都要拿全局锁（BQL）。两颗 CPU 高频轮询 GPIO，加锁解锁本身就是不小的开销。 icount-io.patch 让 TCG 的外设访问路径遵守 memory_region_enable_lockless_io()， RZ/A1H 的 GPIO 和 STM32 的外设区域打开了这个标志：读 GPIO 只是读状态，不再拿锁；写操作和其他外设仍在设备里自己拿锁。 打开频谱时，主界面空闲速度从真实时间的约 15% 提高到约 25%。

关掉 icount、改用多线程（MTTCG，-accel tcg,thread=multi -smp 1,maxcpus=2）能启动，但固件只给副 CPU 200 微秒真实时间来响应请求。 WSL2 里唤醒一个线程、交接一次全局锁就要几十到几百微秒，握手经常超时，固件报“副 CPU 工作不正常”。 icount 模式的时间按指令计算，不受宿主线程调度影响，所以目前仍用 icount。

7尚未仿真的部分

  • 主 DSP 的真实运行：要执行 SHARC 原版固件，需要一个 SHARC 仿真器。Python 写的仿真器每秒只有约 20 万条指令，比真芯片慢上千倍；要让 DSP 跟上，得用 C 写并直接集成进 QEMU。本仓库不含 DSP 仿真器。
  • DV DSP（C55x）：同上。
  • 音频：ARM 的 SSIF、SHARC 的 SPORT、DV DSP 的 I²S、编解码芯片之间还没有样本流动。
  • FPGA 数据面：只有配置握手，没有频谱和中频数据。
  • 射频、Wi-Fi、蓝牙、GPS：不存在。
  • DSP 的版本握手是模拟出来的：开机时 ARM 会向两颗 DSP 询问版本号。DSP 不运行，qemu/ic705/dsp.c 和 dv_dsp.c 按它们固件的做法代为回答，见 7.1 节。

7.1 版本握手的行为模型

原来开机会弹出 “DSP/FPGA 版本不一致”。原因是版本号由 DSP 自己从 SPI 闪存读出、再报告给 ARM，DSP 不运行，ARM 就收不到。现在 qemu/ic705/dsp.c 和 dv_dsp.c 代为回答，数据全部取自闪存：

链路ARM 发出模型回答
主 DSP（RSPI3，握手线 P7_6）E000000k 询问，80000000 轮询拉高 P7_6，回 F + 第 4 个字符的数字 + 前 3 个字符，例如标签前半 “3060” → F0333036（ARM 显示 “3.06”）。标签在闪存 0x40000（DSP 程序）、0x180000（FPGA）、0x80000（DSP 数据）。与真 SHARC 固件在 Python 仿真器里给出的回复逐字节一致。
DV DSP（RSPI0，握手线 P3_8）03 00 00 FF拉高 P3_8，回 16 00 "1.11-000" "1.41-000" 01 01 01 01 FF，两个版本字符串取自闪存 DV DSP 区的 UTF-16 字符串

主 DSP 的模型同时应答启动命令（020000x0，驱动 P7_7）。RZA1H_IC705_DSP_READY=off 和 RZA1H_IC705_DV_READY=off 可以分别关掉。

8如何继续扩展

  1. 找到固件在等什么：开机时用 QMP 每隔几百毫秒执行 info registers，统计 PC 的分布，就能找出固件卡在哪里。
  2. 反汇编那段代码：arm-none-eabi-objdump -d main.elf --start-address=…，读出它访问的寄存器地址和等待的位。
  3. 统计外设访问：QMP 里打开 trace-event memory_region_ops_read on，几秒内就能看出哪个寄存器被读得最多。
  4. 修改或新增模型：改 qemu/machine/ 下对应的 .c 文件，加 rza1h_debug("名字", …) 输出，用 RZA1H_DEBUG=名字 打开。
  5. 重新编译：bash build-qemu.sh，增量编译约 1 分钟。
  6. 对照验证：新行为加环境变量开关，开关两种状态各跑一次，比较截图和时间线。

变量作用
QEMU_ICOUNT_IO_WAIT外设总线等待周期（指令数）；也可以按 CPU 分别设置，如 128,0
QEMU_ICOUNT_RR_WEIGHTS各 CPU 的时间权重，按 CPU 编号
RZA1H_IC705_FPGA=off关闭 FPGA 配置握手模型
RZA1H_IC705_DSP_READY=off关闭主 DSP 的启动应答和版本应答
RZA1H_IC705_DV_READY=off关闭 DV DSP 的版本应答
RZA1H_DEBUG=fpga,rspi,…打开各设备的调试输出（all = 全部）
RZA1H_PINS、RZA1H_ADC_VALS引脚初始电平、ADC 通道初值
RZA1H_IC705_EEPROMEEPROM 镜像文件（设置持久化）
